# Служебные письма APEX

`POST https://2p2p.ru/api/apex/email` принимает готовые регистрационные письма и
восстановление пароля от `apextop.ru`. Роут зарегистрирован без завершающего `/`:
правильный URL сразу отвечает JSON, без перенаправления. Webhook заказов
`/tilda/apex/webhook` и его SMTP/СДЭК-обработка не изменены.

APEX отвечает за код, ссылку, срок действия, капчу, аккаунты и лимиты запросов
пользователя. Здесь проверяется подпись, сохраняется задача и отправляются
переданные `text` и `html`. Сервис не открывает ссылки и не загружает картинки или
другие URL из тела. Содержимое писем не выводится в веб-интерфейсе администратора.

Изменённые файлы:

| Файл | Назначение |
| --- | --- |
| `routers/apex_email.py` | HTTP API, ограниченное чтение тела, безопасные ответы |
| `services/apex_email_contract.py` | HMAC и проверка контракта v1 |
| `services/apex_email_queue.py` | шифрование, транзакции, lease, повторы, очистка |
| `services/apex_email_smtp.py` | MIME, фиксированный отправитель, TLS и коды ошибок |
| `services/apex_email.py` | конфигурация и lifespan сервиса |
| `db/migrations/apex_email_001.sql` | таблицы и индексы отдельной очереди |
| `scripts/__init__.py`, `scripts/apex_email_admin.py` | миграция и безопасный status |
| `config.py`, `requirements.txt`, `main.py` | env, зависимости, подключение API/worker |
| `tests/test_apex_email.py` | проверки без реальной SMTP-отправки |
| `APEX_EMAIL_SERVICE_RU.md` | развёртывание, ограничения и диагностика |

## Конфигурация 2p2p.ru

Добавьте в секреты App Platform, не в Git и не в переписку:

```dotenv
APEX_EMAIL_SERVICE_SECRET=<отдельная случайная строка минимум 32 символа>
APEX_EMAIL_STORAGE_KEY=<отдельный ключ Fernet>
APEX_EMAIL_QUEUE_PATH=/persistent/apex-email.sqlite3
SMTP_HOST=smtp.yandex.com
SMTP_PORT=587
SMTP_USER=sewingnn.notification@2p2p.ru
SMTP_FROM=sewingnn.notification@2p2p.ru
SMTP_PASSWORD=<существующий пароль приложения Яндекса>
```

Путь `/persistent` — пример: замените его путём подключённого постоянного диска
вашей платформы. По умолчанию используется `var/apex-email.sqlite3`. Каталог должен
быть доступен процессу приложения на запись. Для сохранности при пересоздании
инстанса/деплое **нужен постоянный диск**. Локальный временный диск App Platform
этого не гарантирует. Резервное копирование делайте средствами SQLite online backup,
а не копированием одного файла во время работы WAL.

Очередь отдельная от `TILDA_QUEUE_PATH`: письма с кодами нельзя складывать в
незашифрованную очередь заказов. SQLite работает с `WAL`, `synchronous=FULL`,
`secure_delete=ON`; файл имеет права `0600`, новый каталог — `0700`.

Генерация значений выполняется в доверенном локальном терминале. Сразу перенесите
результаты в менеджер секретов; не запускайте эти команды в публичных CI-логах:

```bash
python -c 'import secrets; print(secrets.token_hex(32))'
python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
```

Первый результат — HMAC-секрет: строка UTF-8, **не** декодировать hex. Второй —
независимый ключ шифрования хранилища; сохраняйте его между перезапусками и
деплоями. Нельзя использовать один ключ для обоих назначений. Замена ключа при
наличии зашифрованных задач блокирует чтение/приём: верните прежний ключ. Ротация
возможна после очистки всех активных задач с согласованным перезапуском всех
процессов; старые резервные копии требуют старого ключа.

Отправитель всегда `APEX <sewingnn.notification@2p2p.ru>`, SMTP envelope sender — тот
же ящик, получатель ровно один. Запрос не может передать From, Reply-To, вложения
или настройки SMTP. Порт 587 требует STARTTLS с системной проверкой сертификата
до логина, 465 использует SMTP_SSL. Другие порты и другой SMTP_USER/SMTP_FROM
отключают новый сервис. При пустом/коротком HMAC-секрете, отсутствии ключа
хранения или пароля API отвечает безопасным `503`, остальные части сайта работают.
Существующие обязательные настройки приложения из `config.py` также нужны.

## Настройка APEX

В окружении **магазина APEX**, отдельно от этого репозитория:

```dotenv
EMAIL_SERVICE_URL=https://2p2p.ru/api/apex/email
EMAIL_SERVICE_SECRET=<в точности значение APEX_EMAIL_SERVICE_SECRET на 2p2p.ru>
```

SMTP_PASSWORD магазину для этой интеграции не нужен: он остаётся на 2p2p.ru.
Эта доработка не меняет окружение удалённого магазина автоматически.

## Миграция и запуск

Из корня репозитория, с настроенным окружением:

```bash
python -m pip install -r requirements.txt
python -m scripts.apex_email_admin migrate
uvicorn main:app --host 0.0.0.0 --port 8000 --ws websockets
```

Миграция `db/migrations/apex_email_001.sql` применяется идемпотентно и автоматически
при первом обращении worker/API. Команда `migrate` позволяет проверить настройки,
права записи и миграцию до переключения APEX. Это **SQLite**, не SQL для PostgreSQL;
изменения существующих таблиц заказов не требуются. Фоновый worker запускается
в lifespan FastAPI, отдельный процесс/cron, Node.js, Docker или RabbitMQ не нужны.

Несколько Uvicorn workers на **одном сервере и одном общем локальном диске**
координируются через SQLite и lease с продлением. Не размещайте эту SQLite на NFS
и не запускайте несколько независимых реплик с разными дисками: у них не будет
общей дедупликации. Для такого масштабирования нужна общая транзакционная БД
очереди (например PostgreSQL), а не отдельная копия файла в каждой реплике.

## Подпись и контракт

Принимается `application/json` или `application/json; charset=utf-8`, без сжатия.
Лимит — 128 КиБ, проверяется и для chunked тела без Content-Length. Исходные байты
читаются один раз до JSON-разбора. Подпись:

```python
"sha256=" + hmac.new(
    secret.encode("utf-8"),
    timestamp_header.encode("ascii") + b"." + raw_body,
    hashlib.sha256,
).hexdigest()
```

Заголовки `X-Apex-Timestamp`, `X-Apex-Signature`, `Idempotency-Key` обязательны и
не должны дублироваться. Timestamp — секунды, допускается отклонение до 300 секунд;
подпись содержит 64 строчных hex-символа. Сравнение — `hmac.compare_digest`.
Idempotency-Key должен быть `apex-mail-` плюс исходный `message_id`.
Cookie, Origin, Referer и IP не дают права отправки. Дополнительный браузерный
CORS/CSRF-механизм для этого API не добавляется; авторизация всегда HMAC.

Обязательные поля v1: `schema_version` (целое 1, не bool), UUID `message_id`,
`source="apex"`, `site_url="https://apextop.ru"`, `kind`, один `to`, `subject`,
непустые `text`/`html`, `created_at`, `expires_at`, объект `data`.
`request_context` можно передать пустым объектом; контекст восстановления сохраняется
вместе с письмом и не подменяется IP сервера отправителя.

Типы — только `registration` и `password_reset`. Первый требует строку `data.code`
из шести ASCII-цифр, например `012345`. Второй требует `data.reset_url` вида
`https://apextop.ru/account#reset-password=<URL-safe token>`: без userinfo, порта,
query и других путей/хостов. Поля кода и reset_url взаимоисключающие. Неизвестные
поля, в том числе настройки отправителя/вложения, отклоняются.

Дата — ISO 8601 с timezone. Допускается `created_at` не более чем на 60 секунд
в будущем. TTL с техническим запасом: до 660 секунд для регистрации, до 1860
для восстановления. Новое уже просроченное письмо не принимается. Лимиты полей:
subject 200 символов без управляющих символов, data.name 120, text 65536,
html 98304, reset_url 4096; общий байтовый лимит 128 КиБ действует дополнительно.
Email — одиночный ASCII addr-spec без display-name, списков и управляющих символов;
проверяется синтаксис без DNS-запросов. Дублирующиеся JSON-ключи, NaN и неверный
UTF-8 отклоняются. Ошибки валидации не возвращают исходные значения полей.

## Доставка, повторы и срок хранения

Зашифрованное полное тело, хеш SHA-256 **исходных байтов** и задача сохраняются
одной транзакцией. UUID — PRIMARY KEY. До успешного commit `202` не возвращается.
Повтор UUID с тем же телом даёт `200` без второй задачи даже после отправки или
истечения срока. Повтор UUID с другим телом (в том числе с другими пробелами в
JSON) даёт `409`, исходная задача не меняется. Каждый HTTP-повтор подписывается
заново со свежим timestamp, но тело остаётся тем же.

Worker берёт задачу атомарно под `BEGIN IMMEDIATE`, выдаёт lease 120 секунд,
продлевает его во время SMTP и проверяет token при завершении. После аварии
просроченный lease может взять другой процесс. Плановый shutdown ждёт текущую
SMTP-попытку, а не освобождает lease под работающим потоком.

Перед SMTP проверяется исходный expires_at. Временные SMTP 4xx/сетевые ошибки
повторяются с интервалами 5, 10, 20, 40, 80, 160, 300 секунд до исходного срока.
Постоянная ошибка, например отказ получателя/SMTP 5xx, переводит задачу в `failed`;
безопасный код виден в журнале и команде `status`. Для новой попытки после
исправления пользователь запрашивает новый код/ссылку в APEX.

Более новый `created_at` для того же типа и получателя отменяет старые ещё не
отправляемые задачи. Запоздавшая более старая задача тоже будет отменена. Адрес
для этого сравнения хранится как HMAC-тег с отдельным контекстом ключа хранения,
не открытым текстом. Уже начатую SMTP-отправку отменить гарантированно нельзя.

SMTP Message-ID детерминирован: `<apex.<UUID>@2p2p.ru>`. При потере ответа SMTP
после принятия письма или аварии между SMTP и локальным commit возможна повторная
доставка. Абсолютная однократность SMTP не гарантируется; HTTP-повторы новой
задачи не создают. `202` означает принятие, а не доставку во «Входящие».

После `sent`, `cancelled`, `expired` или постоянной ошибки содержимое удаляется из
строки очереди. Метаданные и SHA-256 сохраняются минимум 7 суток после завершения
для дедупликации. Автоматическая очистка выполняется worker. Очистка строки не
заменяет политику хранения зашифрованных резервных копий.

## Если постоянно возвращается 503

В этом API HTTP 503 появляется **до SMTP**. Подключение к PostgreSQL не участвует
в приёме этих писем: они записываются в отдельную локальную зашифрованную очередь.
Поэтому работающий PostgreSQL и успешное отдельное SMTP-письмо не проверяют
готовность этого endpoint.

В окружении **того же приложения FastAPI** запустите:

```bash
python -m scripts.apex_email_admin doctor
```

Команда проверяет конфигурацию, ключ Fernet, доступ к файлу, миграцию и запись
метаданных очереди. Она не подключается к SMTP и не отправляет писем. Результат
можно безопасно передать для диагностики: значений секретов, адресов клиентов,
текстов писем и путей из ошибок там нет. `ok: true` означает готовность настроек
и локального хранилища; SMTP явно помечается `not_tested`.

Тело ответа API различает две категории:

- `email_service_not_configured`: не прошла проверка env. Команда `doctor`
  перечислит `issues` с кодом и именем конкретной переменной. В серверном логе
  `apex.email` теперь также указывается точная причина вместо общего
  `configuration_required`.
- `queue_unavailable`: конфигурация прошла проверку, но файл/транзакция очереди
  недоступны. В `doctor` и серверном логе будет безопасный код `reason`.

Частые причины:

| Код | Что проверить |
| --- | --- |
| `missing_service_secret` / `service_secret_too_short` | APEX_EMAIL_SERVICE_SECRET задан на backend, минимум 32 символа |
| `missing_storage_key` | задан APEX_EMAIL_STORAGE_KEY, он нужен дополнительно к HMAC-секрету и SMTP-паролю |
| `invalid_storage_key` | ключ хранения получен через Fernet.generate_key(), не через token_hex; это urlsafe-base64 32 байт (44 символа) |
| `storage_key_reuses_service_secret` | ключ шифрования отдельный от секрета подписи |
| `invalid_smtp_from` | SMTP_FROM содержит только sewingnn.notification@2p2p.ru; имя APEX добавляет сам сервис |
| `queue_permission_denied` / `queue_read_only` / `queue_cannot_open` | у пользователя приложения есть права записи в каталог очереди; диск подключён по реальному пути |
| `queue_disk_full` | свободное место и квота диска |
| `queue_busy` | блокировка файла другой транзакцией; несколько процессов должны использовать одну локальную SQLite, без NFS |
| `storage_key_changed` | для существующих активных задач нужен прежний APEX_EMAIL_STORAGE_KEY; вернуть старый ключ, не удалять очередь |

Не создавайте новый ключ поверх очереди с ожидающими письмами. При отсутствии
ключа на первом запуске создайте его по команде из раздела конфигурации и сохраните
в секретах App Platform. Переменные должны быть доступны **во время работы
FastAPI**, не только во время сборки и не только на стороне APEX. После изменения
env перезапустите приложение: настройки читаются при импорте `config.py`.

## Ответы и диагностика

Новая задача: `202 {"ok":true,"message_id":"<исходный UUID>","state":"queued"}`.
Запоздавшая старая задача может сразу иметь state `cancelled`.
Повтор: `200 {"ok":true,"message_id":"<тот же UUID>","duplicate":true}`.
Ошибки: `{"ok":false,"error":"<безопасный код>"}`:

| HTTP | Причина |
| --- | --- |
| 401 | неверная/отсутствующая подпись, формат или timestamp |
| 400/422 | некорректное тело, контракт или Idempotency-Key |
| 409 | UUID уже принят с другим SHA-256 тела |
| 410 | новое письмо уже просрочено |
| 413 | тело больше 128 КиБ |
| 415 | Content-Type/charset/content-encoding не поддерживается |
| 503 | сервис не настроен или очередь/commit недоступны; Retry-After: 60 |

API возвращает `Cache-Control: no-store`. Уровень приложения не записывает raw
body, коды, reset URL, контакты, тексты писем, HMAC-заголовки и пароли в логи.
SMTP debug выключен. Новый роут не проходит через logger тела webhook заказов.
Uvicorn access log содержит метод, путь и HTTP-статус. Внешний reverse proxy/APM
нужно настроить так, чтобы он также не собирал тело/секретные заголовки этого пути.
При необходимости ограничьте частоту на прокси для `/api/apex/email`; ответ
ограничителя должен быть JSON с HTTP 429 и числовым Retry-After, а не HTML/redirect.

Просмотр без расшифровки или показа адресов:

```bash
python -m scripts.apex_email_admin status --limit 50
```

Показываются UUID, тип, состояние, попытки, сроки, время следующего повтора и
безопасный last_error. В логах `apex.email` те же безопасные признаки. Ни текст
письма, ни HTML, ни токены в административный вывод не попадают.

## Проверки и безопасный тест

Тесты используют временную SQLite, вымышленные адреса `example.test` и mock SMTP;
не отправляют реальные письма и не меняют рабочую БД:

```bash
python -m pip install -r requirements-test.txt
python -m unittest tests.test_apex_email -v
python -m unittest tests.test_tilda_webhooks tests.test_tilda_outbox -v
```

Включены UTF-8/HMAC, оба типа писем, точный код/fragment URL в MIME, TLS до логина,
подмена байта тела, лимит chunked-запросов, параллельные POST, конфликт UUID,
потерянный HTTP-ответ, два отдельных процесса, commit failure, шифрование файлов,
смена ключа, рестарт, lease/heartbeat/fencing, backoff, истечение, отмена старых кодов,
очистка содержимого, семь суток дедупликации и отсутствие секретов в ошибках/логах.

Реальную проверку проводите только после настройки обоих окружений и выбора
собственного тестового email: запросите регистрацию/восстановление в APEX для этого
адреса, проверьте 202 с совпадающим UUID, затем `status` → `sent` и полученное письмо.
Повторите тот же JSON с новым timestamp/подписью: ожидается 200 duplicate без
второго письма. `sent` подтверждает приём SMTP-сервером, не размещение во «Входящих».
Не используйте адрес клиента из рабочего заказа как тестовый. В рамках реализации
реальные SMTP-письма не отправляются: тестовый адрес пользователь пока не указал.
