# Волейбол внутри существующего FastAPI

Игра перенесена из `XHackerFinnX/volleyball-online`. HTML, CSS и JavaScript
обслуживаются вашим сайтом; физика, счёт, комнаты и WebSocket работают на Python
в том же процессе FastAPI. Для игры не нужны Node.js, npm, Docker, TURN или
отдельный игровой сервис. Существующая PostgreSQL по-прежнему нужна остальной
платформе; игра её не использует.

| Адрес | Назначение |
| --- | --- |
| Остальные страницы `2p2p.ru` | Существующая платформа FastAPI |
| `https://2p2p.ru/volleyball/online/` | Игра и её относительные ресурсы |
| `wss://2p2p.ru/volleyball/ws` | Соединение игроков с Python-сервером |
| `/volleyball/healthz` | Проверка работы игровой симуляции |

## Развёртывание в App Platform

1. Разверните обновлённый **File-Transfer**, включая папки `games/volleyball`,
   `services` и `routers`. Клонировать игровой репозиторий на хостинге не нужно.
2. Оставьте установку зависимостей `pip install -r requirements.txt`.
   Новых Python-зависимостей игра не добавляет.
3. Из корня File-Transfer запускайте:

   ```sh
   uvicorn main:app --host 0.0.0.0 --port 8000 --ws websockets --workers 1
   ```

   Это ваша прежняя команда с явным `--workers 1`. В App Platform оставьте
   **один экземпляр приложения**, отключите автоматическое увеличение числа
   экземпляров и используйте HTTP-порт **8000**. Комнаты находятся в памяти:
   несколько процессов или экземпляров будут иметь разные комнаты. Перезапуск
   приложения завершает текущие матчи.
4. Домен `2p2p.ru` должен направлять весь путь `/` в это же FastAPI-приложение.
   Сохраняйте полные пути `/volleyball/online/` и `/volleyball/ws`, без удаления
   префикса. Прокси платформы должен поддерживать WebSocket Upgrade на том же
   порту 8000. Отдельный внешний порт для игры не требуется.
5. Сохраните существующие настройки PostgreSQL, SMTP и остальных частей сайта.
   В `ALLOWED_ORIGINS` должен быть точный Origin сайта. По умолчанию уже включён
   `https://2p2p.ru`. Если вы задаёте эту переменную самостоятельно, формат —
   JSON-массив, например:

   ```text
   ALLOWED_ORIGINS=["https://2p2p.ru","http://localhost:8000","http://127.0.0.1:8000"]
   ```

   Для другого домена или `www` добавьте его полный Origin без пути. Браузер сам
   выбирает `wss` для HTTPS и `ws` для локального HTTP; адрес IP в клиенте не нужен.
   Для правильных лимитов по IP настройте доверие к forwarded-заголовкам Uvicorn
   только для прокси вашей платформы (`FORWARDED_ALLOW_IPS`). Значение `*`
   допустимо лишь когда приложение доступно исключительно через доверенный прокси.

После развёртывания проверьте `/volleyball/healthz`: ожидается
`{"ok":true,"protocol":1}`. Откройте игру на двух устройствах: создайте комнату,
передайте четырёхзначный код второму игроку и нажмите «НАЧАТЬ МАТЧ» у хозяина.
Оба устройства должны видеть одинаковый счёт и движения. В DevTools подключение
к `/volleyball/ws` должно получить статус `101 Switching Protocols`.

## Поведение и настройки

Сервер рассчитывает физику с фиксированным шагом 60 Гц и рассылает снимки около
30 раз в секунду. Клиент отправляет только кнопки, а не координаты или счёт.
Параметры матча, пауза, перезапуск и исключение гостя доступны хозяину.
При потере соединения матч приостанавливается; на возвращение игрока отведено
45 секунд. Токен восстановления хранится в sessionStorage вкладки, на сервере —
только его хеш. Закрытие комнаты хозяином завершает её для обоих игроков.

Неактивные комнаты удаляются через 15 минут, максимальная жизнь комнаты — 2 часа.
Подключения ограничены по Origin, протоколу, IP, количеству и частоте сообщений;
медленный клиент не задерживает симуляцию остальных.

Дополнительные переменные необязательны:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `VOLLEYBALL_ENABLED` | `true` | Включить игровой сервер и страницу |
| `VOLLEYBALL_MAX_ROOMS` | `100` | Верхняя граница комнат |
| `VOLLEYBALL_MAX_CONNECTIONS` | `300` | Верхняя граница соединений |
| `VOLLEYBALL_MAX_CONNECTIONS_PER_IP` | `6` | Соединения с одного IP |

Эти границы ограничивают ресурсы; допустимую нагрузку на конкретном тарифе нужно
измерять отдельно. Секреты или ключи API для игры не нужны.

## Плавность и мобильное управление

Свой игрок движется с локальным предсказанием, включая торможение после
отпускания кнопки. Сервер подтверждает номера принятых команд; клиент повторяет
ещё не подтверждённый ввод и плавно согласует позицию с сервером. Остальные
игроки и мяч отображаются с интерполяцией снимков. Нажатия и отпускания
отправляются сразу, удерживаемый ввод обновляется примерно 30 раз в секунду.
Это уменьшает визуальные рывки; реальная задержка сети зависит от соединения.

На сенсорных устройствах слева расположены две кнопки движения, справа —
прыжок. Можно одновременно держать направление и прыгать двумя пальцами.
Отмена касания, потеря фокуса и поворот экрана сбрасывают удерживаемые кнопки.
Доступны вертикальное и горизонтальное положения без перезагрузки страницы;
в горизонтальном режиме меню компактнее, а настройки прокручиваются внутри
окна. Учитываются видимая высота браузера и безопасные отступы экрана.
Арена в горизонтальном мобильном режиме заполняет доступную ширину с запасом
у стен: оба края поля остаются в кадре. Мяч и персонажи сохраняют пропорции;
изменяется отображение площадки, физика и её размеры на сервере остаются общими.

## Пинг и диагностика задержек

В матче под именами виден пинг **хоста** и **гостя** до сервера и обратно (RTT),
обновляемый примерно раз в секунду. Сервер измеряет RTT обменом pong/ack,
а не принимает произвольное число от клиента. Для своего игрока браузер также
измеряет полный запрос/ответ. Роли комнаты не дают преимуществ в передаче:
оба устройства подключаются к FastAPI через WebSocket.

Под счётом показаны полученные обновления в секунду (обычно около 30) и FPS
этого устройства. Сообщения «Высокий пинг», «Данные задерживаются», «Низкий FPS»
и «Сервер занят» помогают отличить сеть, отрисовку и задержки серверного цикла.
В подсказке индикатора есть разброс доставки, размер буфера и задержка цикла.
Высокий RTT не обязательно вызван расстоянием: в него входят маршрут провайдера,
Wi-Fi/мобильная сеть, прокси, очередь сервера и обработка сообщения браузером.
Два игрока в Петербурге всё равно обмениваются данными через сервер в Москве.
Операции SMTP и HTTP СДЭК в асинхронных обработчиках магазина вынесены в потоки:
ожидание ответа внешнего сервиса не должно блокировать цикл игры в FastAPI.
Регрессионная проверка подставляет медленные заглушки, не отправляя настоящих
писем или запросов СДЭК, и проверяет продолжающиеся шаги симуляции.

Снимки рисуются по серверным монотонным часам с адаптивным буфером 45–140 мс.
Короткие паузы сглаживаются ограниченной экстраполяцией. Медленная отправка не
накапливает старые снимки в очереди приложения: хранится последний, а команды
комнат отправляются надёжно по порядку. При отсутствии игровых данных примерно
4 секунды видимая вкладка переподключается и восстанавливает своё место.
Возобновить приостановленный матч после восстановления может хозяин.

## Проверки

Из корня репозитория:

```sh
python -m unittest tests.test_volleyball -v
```

Тесты поднимают настоящий локальный Uvicorn и соединяют WebSocket-клиенты.
Они проверяют физику и очки, общий матч двух игроков, восстановление соединения,
права хозяина, лимиты, некорректные сообщения и доступ к ресурсам. Для этих тестов
PostgreSQL и production-переменные не нужны: используется отдельное тестовое ASGI-приложение.

Дополнительная проверка в двух браузерных контекстах выполняется на уже
запущенном сайте (в отдельном окружении с Python Playwright и Chromium):

```sh
python tests/browser_volleyball.py http://127.0.0.1:8000 --chromium /usr/bin/chromium
python tests/browser_volleyball_prediction.py http://127.0.0.1:8000 --chromium /usr/bin/chromium
python tests/browser_volleyball_mobile.py http://127.0.0.1:8000 --chromium /usr/bin/chromium
python tests/browser_volleyball_network.py http://127.0.0.1:8000 --chromium /usr/bin/chromium
```

Playwright используется только при проверке и не входит в зависимости сайта.
Проверка предсказания охватывает обе роли при 60/120/144 Гц и задержках
0/100/200 мс. Мобильная проверка использует два браузерных контекста,
мультитач и поворот экрана при ширине от 320 до 1024 CSS-пикселей.
Сетевая браузерная проверка создаёт разную задержку для двух игроков и проверяет
показ пинга и восстановление после зависания. Проверка снимков моделирует
разброс прихода пакетов и паузу доставки на 220 мс с последующим приходом пачки.

Для численного замера на запущенном сайте:

```sh
python tests/measure_volleyball_network.py http://127.0.0.1:8000 --seconds 6
```

Скрипт создаёт собственную временную комнату для двух клиентов и выводит RTT,
время подтверждения ввода, частоту/паузы снимков и объём данных отдельно для
каждой роли. Оба клиента работают на машине, где запущен скрипт: локальные
цифры не являются пингом реальных игроков из Петербурга. Для проверки маршрута
до production можно запустить его со своего компьютера, указав `https://2p2p.ru`.
Сетевая проверка выполнялась локально; доступ через публичный домен и прокси
App Platform нужно подтвердить после развёртывания.
