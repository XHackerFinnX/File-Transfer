# Google Таблица для заказов, не записанных в PostgreSQL

При ошибке PostgreSQL заказ остаётся в SQLite. Если настроено резервирование,
сервис также записывает его в Google Таблицу. Таблица — внешняя копия для ручного
восстановления, приложение **не читает из неё заказы** и не импортирует их
автоматически. Успешные обычные заказы в Google не отправляются.

В сессии разработки нет подключения к Google-аккаунту владельца магазина.
Реальная таблица и её URL появятся только после выполнения настройки ниже.
Тестовые spreadsheet ID из тестов не являются рабочими таблицами.

## Настройка существующей/новой таблицы владельца

1. Откройте [Google Таблицы](https://sheets.new), создайте отдельную таблицу для
   резервных заказов и сохраните её URL. В адресе
   `https://docs.google.com/spreadsheets/d/SPREADSHEET_ID/edit` нужен SPREADSHEET_ID.
2. В Google Cloud включите Google Sheets API, создайте сервисный аккаунт и JSON-ключ.
   Полный JSON храните только в секретах приложения. Его не нужно присылать в чат
   или добавлять в Git. Для приложения используется scope `spreadsheets`.
3. Откройте доступ к таблице для `client_email` этого сервисного аккаунта с ролью
   «Редактор». Таблица остаётся закрытой для посторонних. Почту сервисного аккаунта
   можно посмотреть командой `account` ниже — приватный ключ она не выводит.
4. В окружении FastAPI задайте:

```dotenv
TILDA_SHEETS_SPREADSHEET_ID=<ID вашей Google Таблицы>
TILDA_SHEETS_TAB=Webhook backup
TILDA_SHEETS_SERVICE_ACCOUNT_JSON=<полный JSON-ключ сервисного аккаунта>
```

В TILDA_SHEETS_SERVICE_ACCOUNT_JSON нужен целый JSON-объект, выданный Google,
с client_email/private_key и другими полями. Секреты подписи APEX к нему не относятся.

`TILDA_SHEETS_TAB` — отдельный лист внутри таблицы, не имя файла. Если листа нет,
команда `init` создаст его. Остальные листы не меняются. Первая строка листа
зарезервирована под заголовки резервных копий.

```bash
python -m pip install -r requirements.txt
python -m scripts.tilda_sheets_admin account
python -m scripts.tilda_sheets_admin init
```

`init` проверяет запись заголовков и возвращает настоящий `spreadsheet_url`.
После настройки и перезапуска приложения ссылка «Резервная таблица» появится в
кабинете `/tilda/{name}/form?secret=...`.

Если ID и JSON-ключ оба пусты, интеграция отключена и сохраняется прежняя локальная
очередь. Если задана хотя бы одна переменная, резервирование считается включённым:
при неполной/неверной настройке и отказе PostgreSQL webhook не получит ложного
подтверждения внешней копии. Секреты нужны во время работы приложения, не только
на этапе сборки. Существующие настройки приложения и TILDA_PROJECTS_JSON нужны
как раньше. Для HTTP-доступа серверу нужны `sheets.googleapis.com` и
`oauth2.googleapis.com`.

## Создание таблицы командой

При наличии настроенного сервисного аккаунта можно создать таблицу через API,
сразу предоставить доступ владельцу и получить рабочую ссылку:

```bash
python -m scripts.tilda_sheets_admin create --share-with YOUR_GOOGLE_EMAIL
```

Сначала достаточно задать TILDA_SHEETS_SERVICE_ACCOUNT_JSON. Команда вернёт
`spreadsheet_id` и `spreadsheet_url`; полученный ID нужно сохранить в
TILDA_SHEETS_SPREADSHEET_ID. Для создания/предоставления доступа включите также
Google Drive API и доступ сервера к `www.googleapis.com`. Scope `drive.file`
используется только командой создания; worker пишет через Sheets API.

Если Google запрещает сервисному аккаунту создавать файлы из-за квоты/политики
аккаунта, создайте таблицу от своего Google-пользователя через sheets.new и
предоставьте доступ сервисному аккаунту по предыдущему разделу. Если создание
прошло, а предоставление доступа нет, команда выводит созданный URL и код
`sheet_created_but_sharing_failed`; она не выдаёт это за успешную настройку.

## Что и когда записывается

В копии присутствуют все поля таблицы PostgreSQL `tilda_submissions`:

`id`, `site`, `created_at`, `payload_type`, `payload`, `cookies`, `client`,
`headers`, `im_number`, `webhook_key`.

Также записываются target базы, время копирования, безопасный код ошибки,
`backup_id` для идентификации заказа и checkpoints очереди. `submission_json`
содержит полную запись для восстановления; JSON-поля дополнительно вынесены в
отдельные столбцы. Данные пишутся с `valueInputOption=RAW`, поэтому начальные нули
и значения, начинающиеся с `=`, остаются текстом и не выполняются как формулы.

Ограничение Google — 50 000 символов в ячейке. Большие JSON разбиваются на строки
по столбцам `part`/`parts`; части одной копии имеют общий backup_id. Чтобы
восстановить большой объект, объедините содержимое `submission_json` по part
без разделителей. Каждый фрагмент содержит не более 20 000 Unicode codepoints.
Очень длинные вспомогательные текстовые столбцы сокращаются до 20 000 символов;
**полное значение всегда остаётся в submission_json**. Запросы группируются до
примерно 1 МиБ, чтобы не отправлять огромный append одним запросом.

Задача резервирования фиксируется в отдельной таблице `webhook_sheet_backups`
того же файла SQLite. Она не удаляется из-за восстановления PostgreSQL: Google
имеет отдельный worker, блокировку задания с продлением lease и минутные повторы.
При успехе Google проверяется число записанных строк, затем содержимое локальной
задачи-копии очищается. Если Google недоступен, полный JSON сохраняется для повтора
даже после успешного переноса основного заказа в PostgreSQL. Квитанции копий
хранятся семь дней; ожидающие копии по возрасту не удаляются.

HTTP-поведение при включённой интеграции:

- PostgreSQL подтвердил заказ → обычный успех, Google-копия не требуется.
- PostgreSQL недоступен, SQLite и Google подтвердили запись → HTTP 200 с
  `queued:true`, `storage:local`, `external_backup.status:saved`.
- SQLite записала заказ, но Google ещё не подтвердил копию → HTTP 503 с
  `error:external_backup_pending`, `queued:true`, `Retry-After:60`. Копирование
  продолжается в фоне, отправитель также может повторить тот же webhook.

Повтор webhook не создаёт вторую задачу копирования в одном SQLite-файле.
При потере ответа Google после принятия append возможны повторные строки:
абсолютная однократность без чтения/сверки Google не обещается. Совпадающие
backup_id/part позволяют отличить такие строки. Это не создаёт дубли заказов
при ручном восстановлении: используется прежняя дедупликация по проекту/заказу.

## Кнопка «Добавить запись»

В кабинете магазина нажмите «Добавить запись». Доступ защищён тем же secret, что
и кабинет. Можно вставить полную ячейку submission_json (или объект с полем
submission) и нажать «Заполнить поля из JSON», либо заполнить поля вручную.
Исходный JSON самого webhook тоже можно вставить: он заполнит поле payload.

Поля формы: ID записи, текущий магазин, дата с часовым поясом, тип данных,
номер ИМ, ключ заказа и JSON-объекты payload/cookies/client/headers. ID и ключ
можно оставить пустыми для автоматического определения. Магазин фиксирован
адресом кабинета; запись другого магазина отклоняется. Идентификатор уже
существующей другой записи не перезаписывается.

`POST /tilda/{name}/form/submissions?secret=...` принимает эти поля. Ограничение
тела 4 МиБ (с запасом на метаданные исходного webhook до 2 МиБ); обязательны
непустой объект payload и корректная дата с timezone,
если она указана. Дубликат возвращается как duplicate без новой записи.
Запись сначала фиксируется локально и затем передаётся в PostgreSQL, как обычный
заказ. При сбое БД для неё действует та же Google-копия и минутные повторы.

Восстановление добавляет данные заказа, сохраняя im_number и остальные поля.
Оно не отправляет автоматически письмо клиенту и не повторяет обновление СДЭК.
При необходимости письмо можно отправить отдельно из карточки после записи в БД.
Сведения о прежних действиях можно проверить в queue_state_json резервной копии.

## Диагностика и пределы сохранности

В карточке ожидающего заказа отображается «Копия в Google Таблице» только после
подтверждения Google, иначе — «Копия в Google ожидается». В локальной диагностике
есть отдельные счётчики google_backup_counts:

```bash
python -m scripts.tilda_outbox_admin status
```

В логах — события google_backup_saved / google_backup_pending, ID и безопасный
код ошибки. Исходный JSON, контакты и JSON-ключ сервисного аккаунта не логируются.
Основные коды: sheets_credentials_invalid, sheets_permission_or_quota_denied,
sheets_not_found, sheets_invalid_request_or_tab, sheets_rate_limited,
sheets_connection_error. Все они оставляют задачу для последующего повтора.

Внешняя копия защищает от удаления локального диска **после подтверждения Google**.
Если одновременно недоступны и PostgreSQL, и Google, всё ещё нужны постоянный
диск и/или повторы со стороны отправителя; HTTP 503 специально сохраняет возможность
повтора. Этот механизм не делает временный диск постоянным и не восстанавливает
ранее потерянные заказы, которые никуда не попали.

## Проверки

```bash
python -m pip install -r requirements-test.txt
python -m unittest tests.test_tilda_sheets tests.test_tilda_webhooks tests.test_tilda_outbox -v
```

Google HTTP, SMTP и СДЭК в тестах заменены заглушками. Реальные письма и заказы
в Google из тестов не отправляются. SQL-проверки используют отдельную тестовую
схему при TEST_TILDA_DATABASE_DSN. Браузерная проверка новой формы:

```bash
python -m uvicorn tests.tilda_fixture:create_app --factory --host 127.0.0.1 --port 8010
python tests/browser_tilda_restore.py --origin http://127.0.0.1:8010
```
