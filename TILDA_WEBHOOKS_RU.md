# Заказы Tilda и Taplink (Shelwear)

Оба формата принимаются на прежний адрес `POST /tilda/{name}/webhook`.
Адрес кабинета остаётся `/tilda/{name}/form?secret=...`.
Формат определяется по содержимому, поэтому адаптер работает для любого
подключённого проекта, а не только `shelwear`. Менять JSON на стороне магазина
не нужно. Поддерживаются JSON и URL-encoded формы с вложенными JSON-строками.
Заказ также распознаётся внутри `data` и `payload`, включая JSON-строку в поле
`data` формы. JSON в теле запроса определяется по содержимому, даже если
отправитель указал `text/plain` или `application/x-www-form-urlencoded`.

В базе сохраняется исходный `payload`. Для кабинета, статистики, CSV/JSON,
писем и подготовки данных СДЭК создаётся общее представление заказа.
Уже сохранённые заказы Taplink читаются через тот же адаптер при открытии
кабинета: пересылать webhook или менять структуру таблиц не требуется.
Открытие кабинета не отправляет повторных писем и не меняет данные в СДЭК.
Это распространяется и на старые записи с обёрткой `data`, полем `_raw` или
JSON, ошибочно сохранённым как имя поля формы. Страница кабинета и список
заявок отдаются с `Cache-Control: private, no-store`; адреса JS/CSS содержат
версию по содержимому файлов, чтобы браузер получал актуальный интерфейс.

## Соответствие полей Taplink

| Поле | Использование |
| --- | --- |
| `fullname`, `email`, `phone` | Покупатель; резервные значения из `records` и `records_extended.contacts` |
| `order_number`, затем `lead_number` | Номер для покупателя, кабинета и писем: в примере `27` |
| `order_id`, затем `lead_id` | Технический ID для защиты от повторных webhook: в примере `27956212` |
| `budget` | Переданный итог заказа; при отсутствии — сумма товаров и доставки |
| `offers[].amount` | Количество единиц товара |
| `offers[].price_discount` | Цена единицы после скидки; в примере `30`, а не исходные `3000` |
| `offers[].budget` | Сумма строки товара; сохраняется отдельно, чтобы не терять округления |
| `offers[].price` | Исходная цена; резервная цена, если нет суммы строки и цены после скидки |
| `offers[].options` | Размер, цвет; строки вроде `Размер: S` преобразуются в пары параметр/значение |
| `shipping_price` | Стоимость доставки; ноль сохраняется как бесплатная доставка |
| `shipping_fields` | Способ доставки, город, регион, адрес, индекс, получатель, комментарий, код ПВЗ |

`shipping_fields` может быть объектом или JSON-строкой. При повреждённой строке
остальные данные заказа сохраняются, доступные поля доставки берутся из
`records_extended.shipping`. Денежные расчёты адаптера используют `Decimal`.
Суммы в существующем кабинете и письмах отображаются в RUB.
Дополнительные поля, включая промокоды, остаются в исходном JSON и карточке.

Для Taplink смена номера ИМ автоматически вызывается только при явно указанной
доставке СДЭК. Поиск выполняется по номеру покупателя (`27`), затем добавляется
настроенный `prefix_number` аккаунта. Ручная смена доступна в карточке СДЭК.
Клиентский номер и технический ID при этом не переписываются: новое значение
хранится отдельно в `im_number`. Изменение из карточки затрагивает только
выбранную заявку своего проекта. Для Яндекс и других перевозчиков запросы в
СДЭК автоматически не выполняются, их заказы не входят в статистику СДЭК.
Поведение существующих webhook Tilda при автоматической смене номера сохранено.

## Настройки App Platform

В почтовом клиенте имя отправителя писем заказов определяется проектом в URL
`/tilda/{name}/webhook`: `apex` и `apexf1` → `APEX`, `shelwear` → `SHELWEAR`,
`real_baby` → `REAL BABY`, `ama_living` → `AMA LIVING`. Для остальных проектов
используется `{name}` в верхнем регистре с заменой `_` и `-` пробелами.
Например, заголовок письма APEX: `From: APEX <sewingnn.notification@2p2p.ru>`.
Имя берётся из пути проекта, а не из присланного JSON заказа.

Это применяется к автоматическим уведомлениям, в том числе после восстановления
БД и обработки локальной очереди, и к уведомлениям/своим письмам из кабинета
`/tilda/{name}/form`. Реальный SMTP-отправитель остаётся тем же ящиком.
Новые переменные окружения и изменения БД не требуются; имя появится в новых
отправленных письмах. Служебные письма `/api/apex/email` уже используют `APEX`.

Прежняя команда запуска подходит:

```sh
uvicorn main:app --host 0.0.0.0 --port 8000 --ws websockets
```

Проект `shelwear` должен быть добавлен в существующий `TILDA_PROJECTS_JSON`
с `secret`, `database_target` и `cdek_account`. Соответствующий target нужно
добавить в `POSTGRESQL_DATABASES_JSON`; имя базы должно совпадать с настроенным
`POSTGRESQL_DATABASE_SHELWEAR`. Сохраните остальные проекты в этих JSON.
Для доставки СДЭК используется существующий аккаунт из `CDEK_ACCOUNTS_JSON`,
для писем — существующая настройка SMTP. Новых зависимостей приложения нет.

## Если PostgreSQL недоступен

Каждый заказ сначала фиксируется в локальной SQLite-очереди и только после
этого передаётся в PostgreSQL. По умолчанию файл находится в
`var/tilda-outbox.sqlite3`, вне каталога статических файлов, с правами `0600`.
Работа с диском и PostgreSQL выполняется в фоновых потоках, не блокируя игру.
После подтверждённой записи заказа и результатов его обработки в PostgreSQL
тело заказа удаляется из очереди. Компактная квитанция без тела заказа остаётся
на сутки для обработки повторных запросов.

Если сервер БД отключился, webhook получает HTTP 200 только после сохранения
на диске. Ответ содержит `"queued": true, "storage": "local"` и ID заявки.
Если записать на локальный диск тоже нельзя (нет места, прав или файл недоступен),
сервис возвращает HTTP 503 с `Retry-After: 60`, чтобы отправитель повторил запрос.

Фоновая задача повторяет попытки каждые 60 секунд и подхватывает оставшуюся
очередь после запуска приложения. Приложение может запускаться во время аварии
PostgreSQL: проверка соединения и создание таблиц больше не блокируют startup.
Каждый проект обрабатывается независимо; сбой одной БД не останавливает другие.
Несколько Uvicorn workers на одном файле очереди координируются через SQLite
и обновляемые блокировки заданий. Дедупликация PostgreSQL защищает от повторной
вставки, в том числе когда запись завершилась, а подтверждение соединения потерялось.

В кабинете при недоступной БД отображаются локальные заявки с пометкой
«Сохранён локально · ожидает БД» и количеством ожидающих заказов. API списка
возвращает `database_available` и `pending_count`. Ручная отправка письма для
таких заявок недоступна, пока обработка не завершится. Автоматическое письмо
и смена номера СДЭК начинаются после подтверждения заказа в PostgreSQL.

После отправки SMTP или изменения номера СДЭК результат фиксируется локально
перед записью в PostgreSQL. Если сломалась именно запись истории письма или
нового номера, повторяется сохранение результата, а не внешнее действие.
При аварийном завершении процесса прямо во время SMTP нельзя достоверно узнать,
принял ли письмо почтовый сервер. Такой исход отмечается в журнале как
неизвестный, автоматическая повторная отправка пропускается; письмо можно
проверить и отправить вручную из кабинета после восстановления БД.

Переменные окружения:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `TILDA_QUEUE_PATH` | `var/tilda-outbox.sqlite3` | Путь к файлу локальной очереди |
| `POSTGRESQL_POOL_TIMEOUT_SECONDS` | `3` | Максимальное ожидание подключения из пула вместо прежних 30 секунд |
| `POSTGRESQL_CONNECT_TIMEOUT_SECONDS` | `5` | Таймаут установления соединения PostgreSQL |
| `POSTGRESQL_STATEMENT_TIMEOUT_MS` | `10000` | Ограничение времени SQL-запроса, чтобы зависшая БД не удерживала обработку бесконечно |

На App Platform укажите `TILDA_QUEUE_PATH` на **постоянном записываемом диске**,
например `/data/tilda/tilda-outbox.sqlite3`, и сохраняйте весь его каталог
(SQLite использует дополнительные файлы `-wal` и `-shm`). Обычный временный диск
инстанса сохраняет очередь при перезапуске процесса, но платформа может удалить
его при пересоздании инстанса или новом деплое. Для нескольких отдельных
инстансов нужна сохранность диска каждого из них; очередь одного инстанса не
переносится сама на другой.

Журнал содержит получение заказа, ID заявки, тип ошибки (`PoolTimeout`,
`OperationalError` и т. п.), ожидание повторной попытки и успешное восстановление.
Тело заказа, контакты покупателя и строки подключения в сообщения очереди не
выводятся. Ошибки прав СДЭК, например HTTP 403 из присланного журнала, относятся
к внешней интеграции: заказ сохраняется, ошибка отмечается отдельно.

Очередь защищает запросы, принятые **после установки обновления**. Если старый
webhook уже завершился ошибкой и нигде не сохранился, его нужно повторно
отправить со стороны магазина: по одному ID из журнала восстановить товары,
контакты и адрес нельзя.

## Проверки без отправки настоящих писем

```sh
python -m pip install -r requirements-test.txt
python -m unittest tests.test_tilda_webhooks tests.test_tilda_outbox -v
```

SMTP и СДЭК в тестах заменены заглушками. Дополнительно можно задать
`TEST_TILDA_DATABASE_DSN` для тестовой PostgreSQL: SQL-проверки создают и удаляют
только свою отдельную схему `test_tilda_<случайный ID>`.

Для проверки кабинета в Chromium установите Python-пакет `playwright` и запустите
изолированное приложение (в нём SMTP, СДЭК и база также заменены заглушками):

```sh
python -m uvicorn tests.tilda_fixture:create_app --factory --host 127.0.0.1 --port 8006
# В другом терминале:
python tests/browser_tilda_webhooks.py --origin http://127.0.0.1:8006 --chromium /usr/bin/chromium
```

Браузерная проверка использует тестовый endpoint сброса, доступный только в
`tests.tilda_fixture`. Не запускайте эту fixture как рабочее приложение сайта.
